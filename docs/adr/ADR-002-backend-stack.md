# ADR-002 — منصة الخادم: Fastify + PostgreSQL (بدل Supabase) وRedis مؤجَّل

**الحالة:** معتمد بصيغة معدَّلة عن التوجيه v2 (§29 ADR-002).

## السياق
التوجيه يقترح Supabase (Postgres + Auth + Edge Functions) + Redis للترتيب،
لكنه يسمح ببديل أنسب مع توثيق السبب، والملحق (ز) يوجب *أصغر تعديل* على الكود
القائم لا إعادة البناء.

## القرار
1. **Fastify 5 + PostgreSQL 16 مباشرة** (القائم): نموذج "الخادم هو الحكم"
   يحتاج طبقة API حقيقية — إخفاء مفتاح الإجابة، التوقيت الخادمي، ومعاملات
   النقاط الذرّية تُعبَّر مباشرة في كود الخادم بدل الالتفاف على نموذج
   Supabase العميل-أولًا (RLS). PostgreSQL نفسه مُبقى كما يشترط التوجيه.
2. **الترتيب الحي بدون Redis حاليًا:** `leaderboard_scores` كمصدر حقيقة
   بترتيب مركّب (نقاط ↓، وقت ↑، صحيح ↓) + `leaderboard_snapshots` بكاش
   TTL وإبطال عند الكتابة — يحقق وظيفيًا ما طلبه التوجيه (ترتيب حي + تجميد).
3. **عتبة اعتماد Redis:** يُدخل Redis (Sorted Sets + Rate Limiting موزَّع)
   عند أول تشغيل متعدد النسخ أو عند قياس P95 لصفحة الترتيب > 100ms على
   بيانات حقيقية — وهو بند قائم في ROADMAP.

## البديل المرفوض والسبب
- Supabase: يعقّد إخفاء الإجابة والتوقيت الذري، ويستلزم إعادة كتابة خادم
  كامل يعمل ويجتاز 81 اختبارًا.
- Redis من اليوم الأول: تكلفة تشغيلية بلا حاجة مقيسة؛ البنية الحالية تسمح
  بإدخاله لاحقًا خلف واجهة الترتيب دون تغيير بقية النظام.
